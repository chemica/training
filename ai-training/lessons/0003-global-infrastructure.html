Lesson 0003 · Cloud foundations

Place the workload.

Learn how Regions, Availability Zones, edge locations, resilience, and the shared responsibility model shape an AWS design.

35–45 minutes · CLF-C02 foundation used by AIF-C01, DVA-C02, and AIP-C01

1 · Orient

Prerequisite: service, resource, client, and request from Lesson 0002.

Outcome: Given a workload, you can choose a Region, distinguish an Availability Zone from an edge location, and state which resilience responsibilities belong to AWS and which belong to you.

Theme · Why placement is an application decision

In local development, “where the program runs” can feel like an operational detail. In AWS it becomes part of application design. The Region affects latency, price, legal obligations, and service availability. Inside it, Availability Zones affect whether an infrastructure failure becomes a customer-visible outage.

This matters to our document-intake application. Customers may expect UK documents to remain in an approved geography, while the service must continue accepting work when one component fails. AWS supplies resilient infrastructure, but it cannot choose our Region, configure recovery, or test our assumptions. Those remain our responsibilities.

The aim is not to memorise a map. It is to understand how geography, service scope, and responsibility combine into a defensible architecture decision.

2 · Learn the location terms

Region

A separate geographic area in which AWS operates infrastructure. You select a Region for most resources. Selection considers service availability, legal and data-residency requirements, latency, and price.

Availability Zone

One or more discrete data centres with independent power, networking, and connectivity inside a Region. Availability Zones in a Region are connected with high-bandwidth, low-latency networking.

Edge location

A site used by edge services to place content or processing nearer to users. It is not another name for an Availability Zone and is not where you normally deploy a Lambda function or database.

A resource is usually Regional, zonal, or global. The scope affects naming, failure behavior, and architecture. Do not infer scope from the console layout; check the service documentation.

3 · Learn scale and resilience

Scalability
The ability to increase or decrease capacity to meet demand.
Elasticity
The ability to adjust capacity dynamically as demand changes.
High availability
A design goal that keeps a system usable despite component failures, often by using redundant resources across Availability Zones.
Fault tolerance
The ability to continue operating with little or no interruption when a component fails. It usually costs more than a design that restores service after failure.
Disaster recovery
The plan and mechanisms used to restore service and data after a major disruption.

These terms are related but not interchangeable. Auto scaling can improve elasticity. It does not automatically make data durable or a design highly available.

4 · Learn shared responsibility

AWS describes security and compliance as a shared responsibility. AWS is responsible for security of the cloud: facilities, physical hardware, and the infrastructure that runs AWS services. The customer is responsible for security in the cloud: identities, data, configuration, and application behavior.

The boundary changes with the service model. With Amazon EC2, you manage the guest operating system. With Lambda, AWS manages the operating system and runtime infrastructure, while you remain responsible for code, dependencies, permissions, configuration, and data.

Worked example

A UK document assistant handles confidential contracts. The team selects London because of residency requirements and latency. Its API and data services use multiple Availability Zones where the selected managed services support that behavior. Static assets use a content-delivery service with edge locations.

AWS operates the facilities and managed-service infrastructure. The team must still configure IAM, encryption, backups, logging, data retention, application validation, and recovery tests. “AWS is highly available” does not prove that this application is.
