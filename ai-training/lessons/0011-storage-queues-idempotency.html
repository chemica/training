Lesson 0011 · DVA-C02 events and data

Expect duplicate work.

Learn S3 objects, DynamoDB items, SQS delivery, visibility timeouts, retries, dead-letter queues, and idempotent consumers.

50–65 minutes · AWS Certified Developer – Associate

1 · Orient

Prerequisite: synchronous and asynchronous flow, event, queue, function, timeout, throttle, SDK, and execution role.

Outcome: You can design an asynchronous document-processing path that remains correct when messages are delivered again.

Theme · Why reliable systems expect repetition

A document upload may succeed even when the client never receives the response. A queue may deliver the same message again when a worker times out before acknowledging it. Distributed systems therefore cannot treat every repeated request as new work.

Our intake API stores document bytes in S3, records workflow state in DynamoDB, and places processing messages in SQS. Each service has a distinct role. The worker uses an idempotency key so retrying the same logical request does not create duplicate customer records or repeat a costly model call.

Retries help transient failures; a dead-letter queue isolates work that repeatedly fails. Together with observable state, these patterns turn inevitable repetition into controlled behaviour.

2 · Learn the data roles

Amazon S3 stores objects in buckets. An object has a key, data, and metadata. Amazon DynamoDB stores items in tables. Each item is identified by its primary key. S3 suits durable file-like objects; DynamoDB suits low-latency key-based application state.

Amazon SQS stores messages until consumers process and delete them or retention expires. A queue decouples the rate at which producers submit work from the rate at which consumers process it.

3 · Learn delivery and retries

With a standard SQS queue, design for at-least-once delivery: a message can be delivered more than once. After a consumer receives a message, the visibility timeout temporarily hides it. If processing succeeds, the message is deleted. If it is not deleted before visibility returns, it can be delivered again.

A dead-letter queue (DLQ) receives messages after a configured number of failed receives. It isolates persistent failures for investigation. A DLQ is evidence and containment, not an automatic fix.

Exponential backoff increases delay between retry attempts. Add randomness, called jitter, to reduce synchronized retry bursts.

4 · Learn idempotency

An operation is idempotent when repeating it with the same intended request does not create additional unintended effects. Idempotency is essential when delivery and retries can duplicate work.

An idempotency key identifies the logical operation. Before applying an effect, a consumer checks or records the key in durable state. The exact design must handle concurrent consumers and partial failure.

Worked example

S3 records an uploaded document. A message containing document ID and version enters SQS. A Lambda consumer uses document-id:version as an idempotency key in DynamoDB.

If the key already records completion, the consumer acknowledges the duplicate without creating a second summary. If processing fails, SQS makes the message visible again. After the receive limit, it moves to the DLQ. Metrics alarm on DLQ depth and age of the oldest message.

The visibility timeout must exceed expected processing time with margin, or the same message can become visible while the first consumer is still working.
